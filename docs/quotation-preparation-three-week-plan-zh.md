# Quotation Preparation：从下载数据到完成演示的完整 workflow

## 问题说明

**选题：Quotation Preparation（报价单编制）。**

批发和分销公司的销售行政人员需要根据客户询价编制报价单。当客户一次询问多种产品时，员工需要手动查找产品目录、核实价格、计算折扣，再将结果整理成报价文件。这些工作重复、耗时，并且高度依赖员工经验，容易造成报价不一致、回复延迟，在业务繁忙时还可能错失销售机会。

本项目将这一问题具体化为办公设备分销场景：客户提交包含多个产品、数量和规格要求的询价，销售人员需要确认需求、找到合适型号，并给出准确的报价。客户信息不完整或后续修改数量时，还需要补充沟通、重新计算和更新文件。

**要解决的核心问题是：如何把一条客户询价，经过必要澄清、产品查询和规则计价，转成可审核、可修改、可导出的报价单，减少重复查找、计算和录入工作。** 后续 workflow 围绕这一目标展开。

## 先看整个流程

**数据已准备完成（2026-09-14）：**已下载 6 份 Dell 官方英文 PDF，整理出 12 个显示器型号、12 个模拟价格、96 条字段依据，并生成 Agent JSON、CSV 和 SQLite。使用入口见 [数据包说明与运行命令](../data/README.md)，运行时目录为 [catalog.json](../data/agent/catalog.json)。产品查询和计价已有可调用的离线工具，14 项工具测试通过；模型接入、网页、报价保存与 PDF 导出仍是后续工作。数据包提供 Bedrock Converse 工具配置，尚未上传 AWS 或调用模型。

按照以下顺序执行，完成当前步骤的检查后再进入下一步：

> 确定产品范围 → 下载产品资料 → 提取并核对规格 → 整理产品表 → 添加模拟价格与规则 → 校验并导入数据库 → 实现查询与计价 → 接入报价 Agent → 制作网页 → 保存与导出报价 → 处理修改和异常 → 验收 → 录制 30 分钟视频。

以下保留完整操作流程，便于复现和扩展。已完成的数据文件和脚本以数据包说明为准，无需从头重新下载。可以让开发 Agent 逐步执行后续任务，每次检查实际文件或运行结果后再继续。

三周内的阶段目标是：第一周完成数据和最小报价流程；第二周完成页面、PDF、版本修改及异常处理；第三周测试、修复和录制视频。以下不再按人员或每天分配任务。

## 步骤 1：固定第一版要处理的业务

第一版做一个虚构办公设备分销商的报价助手，先从 **10 个显示器型号** 开始，流程跑通后扩展到约 30 个产品。配套键鼠可以后加，不影响显示器多型号报价。

固定以下范围：

- 输入：英文客户询价，可以包含多个型号或规格要求、数量和预算。
- 产品：只从本地目录选择，保留原始资料依据。
- 价格：SGD，使用明确标注的模拟销售价。
- 输出：可修改的报价草稿、PDF 和版本差异。
- 操作：用户确认后导出，原型不实际发送报价或创建采购订单。

准备一句贯穿开发的需求：

> We need 8 monitors for our new office. They should connect to our laptops through USB-C. Our budget is SGD 2,500.

这里还缺少 USB-C 是否需要供电等信息，系统应该追问。预算是否可满足，等实际目录和模拟价格准备好后再判断。

**本步产物：**一份简短的范围说明。将数据方案写清楚：“公开产品规格 + 模拟销售价格和业务规则”。使用前确认主办方接受这种数据组合。

## 步骤 2：建立存放数据的位置

先建立目录，原始文件、整理结果和测试案例分开存放：

```text
 data/
   raw/                          # 下载的原始资料，不覆盖
     dell/                       # 产品说明书 PDF

   processed/
     products.csv                # 已核对的产品规格
     prices.csv                  # 模拟销售价
     pricing_rules.json          # 模拟计价规则
     sources.csv                 # 来源与下载记录
     field_evidence.csv          # 关键字段对应的原文位置
   evaluation/
     enquiries_dev.jsonl         # 开发时使用的询价
     enquiries_holdout.jsonl     # 最后验收时使用的询价
     expected_results.jsonl      # 人工核对的答案
   README.md                     # 字段、来源与模拟内容说明

```

`raw` 中保留下载原件。即使提取结果有错误，也可以回到原文重新核对。

**给开发 Agent 的指令：**

> 按文档建立数据目录和来源记录模板。先不生成产品规格或销售价格，所有尚未获得的内容保持为空。

**完成检查：**能够清楚区分原始资料、待核对数据、已核对数据和模拟规则。

## 步骤 3：下载第一批产品资料

### 3.1 推荐路线：下载品牌官方说明书 PDF

这条路线适合先准备少量产品，不需要先接入一个完整数据平台。

1. 打开 [Dell Singapore 显示器目录](https://www.dell.com/en-sg/shop/monitors-monitor-accessories/sac/monitors?~ck=bt)。
2. 选择一个具体型号，记录完整型号，不能只记“27 英寸显示器”。
3. 在该型号的支持页面进入 **Manuals & Documents**，寻找 **User’s Guide** 或规格文档。
4. 打开文档并下载 PDF，存入 `data/raw/dell/`。
5. 按 `品牌_型号_文档类型.pdf` 命名，例如 `Dell_S2725DC_user_guide.pdf`。
6. 在 `sources.csv` 记录型号、来源页面、实际文件下载链接、下载日期、本地文件位置及使用说明。
7. 打开下载的 PDF，确认它属于目标型号，能够读取，并且包含产品规格。
8. 重复以上过程，先收集 10 个规格有差异的型号。

可从这个已核对的入口开始：[Dell S2725DC 官方手册页面](https://www.dell.com/support/product-details/en-us/product/s2725dc-monitor/resources/manuals)。该页面列出用户指南等资料，用户指南包含产品功能与规格。页面可能按地区重定向，以实际打开的目标型号为准。

挑选产品时覆盖：不同尺寸、不同分辨率、支持与不支持 USB-C 视频、不同 USB-C 供电能力。不要为凑数量下载十份几乎相同的产品。

如果网页只有在线规格，没有独立 PDF，可以将规格页面打印保存为 PDF，并记录它是网页快照。若找不到明确规格，换一个资料完整的型号；不要让模型补全真实产品参数。

只需下载规格或用户指南，不需要固件、驱动程序或整个售后资料包。公开可下载不等于可以随意重新分发，项目使用事实字段并保留来源；公开提交原始文件前检查来源条款。

**完成检查：**至少 10 份有效资料，能与 10 个型号一一对应；只有产品目录链接、没有具体型号资料不算完成。

### 3.2 备选路线：从 Open Icecat 下载 XML

如果更希望直接处理结构化数据，可以改用这条路线。两条路线任选一条起步，不必重复采集相同产品。

1. 打开 [Open Icecat 订阅页](https://icecat.com/content-subscription/)，注册并激活免费账户。
2. 在 [Icecat 产品目录](https://icecat.biz/) 搜索完整型号，核对品牌和产品代码，确认该资料在账户可访问范围内。
3. 取得该记录的 Icecat ID，或使用官方 XML 手册中的请求生成器按品牌和产品代码生成链接。
4. 请求英文产品 XML；导出地址格式如下，将占位符换成实际 ID：

```text
https://data.icecat.biz/export/freexml/EN/<ICECAT_ID>.xml
```

5. 按账户要求完成身份验证。将返回的 XML 保存到 `data/raw/icecat/品牌_型号.xml`。
6. 检查文件是否包含对应产品信息，而不是权限或错误响应。仅有 HTTP 200 不能证明拿到了有效产品数据。
7. 记录来源、ID、日期和本地文件位置，然后下载其他可访问型号。

端点、请求生成器和错误说明见 [Icecat 官方 XML 手册](https://iceclog.com/open-catalog-interface-oci-open-icecat-xml-and-full-icecat-xml-repositories/)。若出现账户未激活、IP 限制或免费目录不覆盖，按手册处理或换回官方 PDF 路线，不将访问失败内容导入。

Icecat 的使用说明要求相应署名、链接和免责声明，并禁止用于 AI 训练。使用前落实其条款；本项目使用目录查询，不做模型训练。来源说明核对日期：2026-09-06。

**给开发 Agent 的指令：**

> 根据我已激活的账户和选定型号，按官方 XML 文档生成小批量下载脚本。凭据从本地配置读取，不写进源码或日志。每个文件检查产品身份与错误响应，并写入来源记录。只下载目标型号。

**完成检查：**拿到有效产品 XML；账号、产品覆盖或使用条款尚未明确时，不把“免费目录”当作所有型号都可用。

## 步骤 4：把下载文件提取成候选产品数据

此时拿到的是原始资料，还不能直接作为最终产品表使用。

1. 选择一份文件，先提取一个产品，验证方式正确后再批量处理。
2. PDF 优先提取文本，定位“Specifications”“Connectivity”“Power Delivery”等相关段落。表格错位时回看对应页面；文本确实不可提取时，再对相关页面使用 OCR。
3. XML 按实际字段和功能名称解析，不把某个字段在一个产品中出现的位置硬编码为所有产品的位置。
4. 提取型号、名称、尺寸、分辨率、USB-C 视频支持和供电功率。
5. 每个关键字段保存原文位置：PDF 的实际页码与短摘录，或 XML 中的字段名称、路径与值。
6. 输出候选结果到 `data/extracted/`，未知值设为 `null`，冲突写入待核对列表。

**给开发 Agent 的指令：**

> 读取 data/raw 中的资料，先提取一个产品，输出候选 JSON 和字段依据，再批量处理。每个关键规格附本地文件位置及 PDF 页码或 XML 字段。不要推断未写明的参数，不要把同一手册中其他型号的数据混入当前型号。

特别检查两个不同概念：

- USB-C 视频输入：能否通过 USB-C 显示画面。
- USB-C Power Delivery：能否通过连接给笔记本供电，以及功率是多少。

“有 USB-C 接口”本身不足以证明上述两项都满足。

**完成检查：**每个候选产品都能回到原始文件核对；缺失与冲突没有被模型悄悄补齐。

## 步骤 5：核对并整理成统一产品表

逐个核对型号和用于筛选的关键规格，然后写入 `data/processed/products.csv`。

建议固定表头：

```csv
sku,brand,model,name,category,unit,screen_inches,resolution,usb_c_video,usb_c_pd_watts,aliases,source_id
```

字段规则：

| 字段 | 怎么填写 |
|---|---|
| sku | 自建唯一编号，例如 MON-001；后续价格和报价都用它关联 |
| brand、model | 保留官方品牌与完整型号 |
| category、unit | 第一版使用 monitor、piece |
| screen_inches | 数值，例如 27；单位不再重复放进值 |
| resolution | 统一为类似 2560x1440 的写法 |
| usb_c_video | true、false 或空值；空值表示未知 |
| usb_c_pd_watts | 数值；只有原文明确无供电时才用 0，否则未知留空 |
| aliases | 常见简称，用固定分隔符存储，不能把不同型号设成同一个明确别名 |
| source_id | 关联 sources.csv 中的记录 |

`field_evidence.csv` 使用 `sku,field,value,source_id,locator,excerpt`，让规格能追溯到具体原文。提取错误在候选数据中修正并重新输出，不修改原始 PDF/XML。

下面只是格式示例，产品是虚构的，不能作为某个真实型号的规格：

```csv
sku,brand,model,name,category,unit,screen_inches,resolution,usb_c_video,usb_c_pd_watts,aliases,source_id
MON-DEMO,DemoBrand,D27,Demo 27 Monitor,monitor,piece,27,2560x1440,true,65,Demo27,SRC-DEMO
```

**完成检查：**SKU 唯一，单位一致；不存在把“未知”当作“否”的情况；同一型号没有混入其他型号的参数。

## 步骤 6：补充报价必需的价格和业务规则

产品说明书通常不能提供我们虚构分销商的销售价格，因此价格要单独创建并标为模拟。不要把网上零售价描述为内部批发价。

### 6.1 创建 prices.csv

```csv
sku,currency,unit_price_cents,price_version,price_source_type
MON-DEMO,SGD,20000,v1,synthetic
```

上例表示虚构产品单价 SGD 200.00。价格使用整数分存储，每个可售产品必须有一条当前版本价格。为真实目录产品配置模拟销售价时，同样标记为 `synthetic`。

### 6.2 创建 pricing_rules.json

第一版可采用这套模拟政策：

```json
{
  "rule_version": "v1",
  "currency": "SGD",
  "discount_limit_bps": 500,
  "rounding": "half_up_per_line_discount",
  "shipping_fee_cents": 0,
  "validity_days": 7,
  "tax_mode": "not_modelled"
}
```

含义：折扣上限 5%；默认折扣为 0；配送费为 0；报价有效期 7 天；暂不单独建模税费。页面和 PDF 注明这是模拟报价及其税费范围。

固定公式：

```text
行原价 = 单价（分）× 数量
行折扣 = half_up(行原价 × 折扣基点 ÷ 10000)
行净额 = 行原价 − 行折扣
总额 = 所有行净额之和 + 配送费（分）
```

数量必须为正整数，折扣必须在允许范围内。折扣由用户明确确认，不由 Agent 为了满足预算自行增加。

### 6.3 手工核对金额

准备至少 5 个答案，包含正常计算、零折扣、上限折扣、半分舍入和非法输入。例：产品 A 单价 SGD 200、数量 3、折扣 5%；产品 B 单价 SGD 40、数量 2、无折扣，总额应为 SGD 650。

**给开发 Agent 的指令：**

> 根据已确认的产品 SKU 创建独立模拟价格表和上述规则文件。检查所有产品都有当前版本价格，价格不写回公开规格数据。按照规定公式生成计算模块，并用我已核对的答案测试。

**完成检查：**真实规格与模拟价格能明确区分，任何人都能只看规则和条目手算出报价。

## 步骤 7：校验数据，再导入数据库

先创建 `scripts/validate_data.py`，读取已整理文件并检查：

1. 产品 SKU 是否重复。
2. 价格 SKU 是否存在，是否有重复的 SKU 与价格版本组合。
3. 价格是否为非负整数分，币种是否一致。
4. 产品是否缺少来源记录，关键规格未知是否保留为空。
5. 显示器尺寸、供电功率等是否具有正确的数据类型。
6. 每个参与报价的产品是否有价格，规则文件是否完整。

发现错误时输出文件、行号、字段和原因。错误修复后再创建导入脚本，把数据导入本地数据库，例如 `storage/app.db`。

数据库至少包含产品、价格、规则版本、报价和报价条目。来源依据可以作为独立表或关联数据保存。创建报价时保存产品名称、单价和规则快照，不能只依赖随时可能更新的目录记录。

**给开发 Agent 的指令：**

> 实现数据校验与导入脚本。先校验，失败时停止导入；成功后导入本地数据库。再次导入同一版本不能生成重复记录。提供一条查询，证明能按 SKU 读到规格、价格及来源。

**完成检查：**数据库中产品数与 CSV 一致；随机查看 3 个产品，原始资料、整理表和数据库中的关键字段相同。

## 步骤 8：先实现不依赖模型的查询和报价

在接入语言模型前，让程序先能完成确定性业务操作：

| 操作 | 输入 | 输出 |
|---|---|---|
| search_products | 名称或结构化规格条件 | 候选 SKU、规格、来源 |
| get_product_price | SKU、价格版本 | 单价、币种、单位 |
| calculate_quote | SKU、数量、折扣 | 行金额、总额、校验错误、价格与规则版本 |

执行以下顺序：

1. 按完整型号查找，确认能得到正确 SKU。
2. 按“USB-C 视频且供电至少 65W”过滤，确认未知规格不被视为满足条件。
3. 传入已确认 SKU 和数量，计算报价。
4. 用步骤 6 的人工答案检查金额。
5. 传入未知 SKU、数量 0、缺价和折扣 6%，确认返回明确错误。

后端按 SKU 查询价格，不能信任前端或模型传入的任意单价。

**完成检查：**即使还没有聊天界面，也能通过接口或简单表单查产品并得到正确报价。

## 步骤 9：接入产品内的报价 Agent

准备可用模型 API，并在后端配置密钥，不能把密钥放进网页或录屏。让模型处理语言，调用步骤 8 已验证的工具。

1. 将询价转成结构化需求，例如产品类别、数量、预算、接口要求。
2. 检查必要字段，缺少数量或关键规格时追问。
3. 将用户补充内容合并到已确认需求，不清空之前的信息。
4. 调用 `search_products`，展示候选依据。
5. 用户确认产品后调用 `calculate_quote`。
6. 根据工具返回结果解释价格，不自行重写金额。

例如用户只说“USB-C 显示器”，可以追问是否需要通过同一根线为笔记本供电，再以确定的要求搜索。

**给开发 Agent 的指令：**

> 把需求提取和澄清接入现有产品查询、计价工具。产品参数和价格必须来自工具返回；未知字段保持未知。记录每次工具调用及状态。先用一条两轮询价验证，再增加其他案例。

模型调用失败时保留当前需求和草稿，允许重试。用户也能绕过对话，通过表单选择产品和数量。

**完成检查：**“询价 → 追问 → 用户回答 → 产品选择 → 计价”在真实 API 调用中运行成功，不依赖预先写死的回复。

## 步骤 10：把已有流程接到网页工作台

页面采用三个区域：

- 左侧：询价输入、对话与已确认需求。
- 中间：候选产品、规格依据、工具执行状态。
- 右侧：报价条目、数量、折扣、总额及操作按钮。

按顺序接入：

1. 输入询价并显示澄清问题。
2. 点击选择一个候选产品，加入报价。
3. 修改数量或折扣，调用后端重新计算。
4. 显示未完成字段、无匹配和计算失败，不把失败显示为空白报价。
5. 增加保存草稿，刷新页面后可以恢复。

界面展示的是实际查询与计算记录，例如“找到 3 个候选”“重新计算完成”，不需要展示模型内部推理。

**完成检查：**通过浏览器完成一条询价并保存；刷新后需求、产品和金额保持一致。

## 步骤 11：生成 PDF，再实现报价修改

### 11.1 导出第一版

1. 固定报价模板：编号、日期、有效期、客户显示名、产品明细、折扣、总额及模拟条款。
2. 用户点击确认，后端检查必填字段与计算结果。
3. 导出该已确认版本的 PDF。
4. 打开 PDF 检查金额、长产品名称、表格分页和页边距。

PDF 使用已保存的报价快照，不在导出时让模型重新生成产品或价格。

### 11.2 修改并保存第二版

1. 用户输入“显示器从 8 台改成 10 台”，或直接修改数量。
2. 从当前版本创建新草稿，保留原版。
3. 使用同一报价锁定的价格和规则版本重算；若需要重新取最新价，作为明确操作另行确认。
4. 显示条目、数量和总额的差异。
5. 用户确认后导出第二版 PDF。

如果用户同时改预算，重新判断是否满足预算。超预算不能靠偷偷修改单价或折扣解决。

**完成检查：**第一版保持不变，第二版金额正确；每版 PDF 都对应自己的条目和价格。

## 步骤 12：补齐异常处理

逐项操作，确认系统行为：

| 输入或故障 | 应有结果 |
|---|---|
| 未提供数量 | 追问，不默认数量为 1 |
| 找不到型号 | 提示无匹配，允许重新描述或手动选择 |
| 必要规格未知 | 标记待确认，不将其推荐为已满足 |
| 预算不足 | 显示差额；有合适替代项时解释取舍 |
| 请求 6% 折扣 | 阻止按该折扣确认，显示 5% 上限 |
| 价格查询失败 | 阻止完成报价，不猜价格 |
| 模型 API 失败 | 保留状态，可重试或手动继续 |
| PDF 导出失败 | 保留草稿，允许再次导出 |
| 重复点击保存 | 不创建重复的同一次修改 |

**完成检查：**异常不会产生一份看似正常但事实或金额错误的已确认报价。

## 步骤 13：创建询价测试集并验收

产品数据用于查询，询价数据用于检查系统行为，不需要模型微调。

1. 创建 20 个开发场景，放入 `enquiries_dev.jsonl`，用于前面步骤调试。
2. 另准备 20 个独立验收场景，放入 `enquiries_holdout.jsonl`，使用不同表达和产品组合，不把答案放入模型提示词。
3. 为每例标注应提取字段、必要追问、可接受产品和预期状态。
4. 对已经确认产品和数量的案例，人工计算预期金额；有歧义的案例应标注“需要澄清”，不强行编一个报价答案。
5. 流程完成后运行独立验收集，保留首轮结果。
6. 修复发现的问题并重测相关案例，区分首次结果与修复后结果。

两组场景都覆盖完整需求、缺项、规格歧义、无匹配、预算不足、数量修改及折扣限制。工程故障另行模拟注入。

最终记录：

| 检查内容 | 记录方式 |
|---|---|
| 任务是否正确处理 | 通过案例数 / 总案例数；正确拒绝或追问也算通过 |
| 产品与价格是否有依据 | 核对进入报价的所有 SKU 和价格来源 |
| 金额是否正确 | 与人工答案逐项对照 |
| 修改是否正确 | 旧版、新版和 PDF 一致性 |
| 使用时间 | 5 个相同案例，分别记录人工与工具辅助完成耗时 |

所有计价和限制测试应通过后再录正式视频。小样本耗时报告实测值，不提前写“提升 80%”。

**给开发 Agent 的指令：**

> 建立询价评估脚本，按预期字段、必要澄清、可接受 SKU 和金额检查结果，不按回复措辞逐字评分。保存逐例结果，人工核对失败项和重要金额；不要把测试答案传给产品 Agent。

**完成检查：**有一份可以展示的实测报告，而不只是成功演示截图。

## 步骤 14：把流程组织成 30 分钟视频

先固定目录、价格和演示案例，使预算转折由实际数据触发。准备三个片段：完整询价、客户修改与折扣限制、模型失败后手动继续。

| 时间 | 内容 |
|---|---|
| 00:00–03:00 | 销售人员收到询价，解释人工找产品与制作报价的问题 |
| 03:00–06:00 | 展示资料怎么下载、如何整理、哪些字段是模拟的 |
| 06:00–14:00 | 实际演示澄清、查询、计价、确认及 PDF |
| 14:00–19:00 | 修改数量、对比版本、处理超限折扣及 API 失败 |
| 19:00–23:00 | 解释 Agent 与查询、计算、保存工具如何连接 |
| 23:00–27:00 | 展示测试结果、金额核对和耗时比较 |
| 27:00–29:00 | 用真实例子说明开发 Agent 如何辅助提取数据或实现功能 |
| 29:00–30:00 | 展示最终报价和交付结果 |

录制顺序：先完整彩排一次 → 修复影响演示的问题 → 录主流程与补充画面 → 剪辑字幕 → 全片检查 → 按官方格式导出和提交。若剪去等待或使用回放，应在相关片段说明。

保证原始规格、CSV、页面、报价 PDF 和视频中的示例能对应。重新录制前恢复固定演示数据，避免不同片段金额不一致。

## 步骤 15：完成交付检查

按顺序检查：

1. 按 README 从干净环境启动，并成功导入数据。
2. 密钥通过配置提供，源码和视频中没有凭据。
3. 完整执行一次询价、澄清、选型、计价、保存、导出和修改。
4. 示例 PDF 正常打开，金额与页面一致。
5. 数据来源、使用说明及模拟价格标注完整。公开数据包按来源许可包含可分发内容；不可重分发的原件提供获取说明。
6. 测试结果与视频中的结论一致。
7. 视频时长、格式和提交内容符合赛事要求，提交后保存确认信息。

最终应得到：可运行项目、可复现的数据准备流程、产品与价格数据、规则文件、测试集与结果、示例报价 PDF，以及 30 分钟视频。

三周进度以这三个结果为准：**第一周能用数据生成草稿；第二周能完整导出和修改；第三周能用测试与视频证明流程可运行。**
